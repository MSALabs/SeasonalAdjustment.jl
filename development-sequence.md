# SeasonalAdjustment.jl — Development Sequence

## What this is, and the one deliberate exception at its core

SeasonalAdjustment.jl is the destination the broader TSAnalytics.jl
project was originally built toward: official-statistics-grade
seasonal adjustment for Julia — X-11, RegARIMA, and SEATS.

**It also deliberately breaks from that project's own "reference, never
port" principle**, for this package's core functionality specifically.
Rather than reimplement X-11/RegARIMA/SEATS from scratch as a first
step, this package wraps the actual Census Bureau X-13ARIMA-SEATS
binary directly — confirmed, not assumed: `x13org/x13prebuilt` on
GitHub is the exact repository R's own `seasonal`/`x13binary` packages
depend on internally, and Python's `statsmodels.tsa.x13` calls the same
program too. Both of the usual reference ecosystems already trust this
binary for the hardest part of the whole problem — SEATS's spectral
factorization especially. Wrapping it directly gets this package to
correct, production-grade output immediately, rather than spending
months on the hardest mathematics in the entire TSAnalytics.jl roadmap
before shipping anything.

A from-scratch native Julia engine remains a real, planned track
(Part 2 below) — not abandoned, deliberately sequenced behind a working
wrapper.

## Relationship to TSAnalytics.jl

**Confirmed**: `tsvalues`/`tsindex` (TSAnalytics.jl's container-agnostic
series interface) as a baseline dependency either way, so a user can
pass the same series object to either package consistently.

**Open, flagged honestly rather than assumed**: whether `X13Result`
(W.4) should subtype an existing TSAnalytics.jl decomposition abstract
type, if `classical_decompose`/`stl_decompose` share one — this needs a
direct check against the real TSAnalytics.jl source before W.4 is
implemented. If a shared type exists, `X13Result` should subtype it for
consistent display/composition; if not, the light dependency above is
sufficient for Part 1. **Do not guess on this — check the source
directly as the first step of W.4's own handoff, not before.**

Part 2 needs the full, deep dependency regardless of how the above
resolves: Stage 8.3 (`fit_arimax`/`fit_sarimax`), Stage 6.8
(`auto_arima`), Stage 6.3 (the Kalman smoother), and Stage 2.4
(Ljung-Box) from that project directly.

## API design principle — a genuine superset of R and Python, verified precisely

R's `seas()` and Python's `x13_arima_analysis()` are differently
*shaped*, not just differently named, confirmed directly:
```r
seas(x, xreg=NULL, ..., list=NULL)   # `...` accepts ANY spec.argument combination directly -- the full X-13 grammar, dynamically
```
```python
x13_arima_analysis(endog, maxorder=(2,1), maxdiff=(2,1), outlier=True, trading=False, ...)  # a fixed, curated subset only
```
**R exposes the entire X-13 spec grammar dynamically; Python exposes
only a curated subset of it.** Being a genuine superset of both
therefore means R's full-passthrough mechanism is the *foundation*,
with Python's curated option list layered on top for discoverability —
not the reverse. Julia's own `kwargs...` maps onto this directly:
```julia
x13(y; maxorder=(2,1), outlier=true, trading=false,   # Python-style curated ergonomics
       regression_variables=[...], arima_model="...", # R-style direct spec passthrough
       kwargs...)                                      # anything else, forwarded straight into spec generation
```
This is a concrete design requirement for W.4 now, not an aspiration —
confirm both mechanisms are genuinely present before treating that
stage as complete.


## Verification philosophy — Part 1 and Part 2 are genuinely different, stated plainly so they don't get blurred

**Part 1 (the wrapper)**: "matches R" and "matches Python" both reduce
to the same claim — "matches `x13prebuilt`'s own real output" — since
neither reference independently computes anything here; both call the
identical binary this package wraps. Primary verification is therefore
direct binary invocation, already proven working (see the real ground
truth already generated, below). R's and Python's own wrapper packages
serve as a secondary check on *API-level* behavior only.

**Part 2 (the native engine, once started)**: genuine independent
reimplementation, so the full TSAnalytics.jl dual-verification standard
applies exactly as it did throughout that project — real R and Python
execution wherever reachable, with `x13prebuilt`'s own output available
as an even stronger ground truth than usual (confirmed directly: this
program includes X-11, RegARIMA, *and* SEATS all in one binary, so
every native-engine stage has real, authoritative output to check
against, not just a published algorithm description).

**The pinned `x13prebuilt` commit**: `61c4043949f43c1ea5ad0fbbc7b6c11fc5073d19`.
Real SHA256 hashes for every platform binary at this commit are already

**The core Box-Jenkins airline passengers series** (1949-1960, 144
monthly observations — the standard benchmark in this entire field),
run through the real binary twice:

*Without any custom regressor* — real D10 (seasonal factors), D11
(seasonally adjusted), D12 (trend-cycle) tables generated directly:
```

                    1.00514879872191, 0.999732566557629, 1.07303952726698

D12, Jan-Mar 1949: 123.774514749304, 123.950693749510, 124.289377383170
```

*With a synthetic Diwali-effect user-defined regressor* (proving the
custom-holiday-regressor mechanism, section "W.0" below) — the same
series, same spec otherwise, but with
`regression { variables=(td) user=(diwali) usertype=(holiday) data=(...) }`
added:
```
D10, October factors WITHOUT the custom regressor: 0.898593816033472 (1949), ...
D10, October factors WITH the custom regressor:    0.726751422651829 (1949), ...
```
**The seasonal factor genuinely shifted** — proof the binary actually
used the custom regressor, not just accepted and ignored it.

Two real, practical requirements surfaced while getting this clean run,
both worth keeping for W.2's spec generation:
1. **User-defined regressor data must cover the RegARIMA forecast
   horizon** (a year ahead, by default), not just the historical series
   length — the binary errors clearly (`"forecasts end date ... must
   end on or before user-defined regression variables end date"`) if it
   doesn't, rather than silently truncating.
2. **Combining a RegARIMA model with multiplicative X-11 mode needs an
   explicit `transform { function = log }` spec** — without it, the
   binary errors (`"Multiplicative or log additive seasonal adjustment
   cannot be performed when preadjustment factors are derived from a
   regARIMA model for data which have not been log transformed"`).

All spec files and full 144-month output tables from both runs are
preserved in this package's verification assets — reuse them directly
as test fixtures rather than regenerating from scratch.

## Post-push finding (2026-08-28): local verification had a real blind spot, caught only by actually pushing to CI

Every prior "confirmed" claim above about Windows/macOS artifact resolution, and every green local test run through W.0-W.4, was genuinely true *for what it tested* -- but local testing never actually exercised a completely fresh dependency/artifact install the way a real new user or CI runner does. Pushing this repo and checking the actual GitHub Actions results (prompted directly by being asked "pushed, now?" rather than assumed) surfaced two real, previously-invisible bugs, both now fixed and confirmed via a genuinely clean-room reproduction (an isolated `JULIA_DEPOT_PATH`, no local package caches, no manually-pre-run tooling) rather than just re-patched and hoped:

1. **Every single CI run, on every commit since the project's first scaffold, had been failing** at the dependency-resolution step (`julia-buildpkg`), with `ERROR: expected package TSAnalytics [b1a2c3d4] to be registered`. TSAnalytics.jl isn't published to Julia's General registry -- `Project.toml`'s `[deps]` entry alone can't tell `Pkg.instantiate()` where to get it from. Local development never hit this because every local session had `TSAnalytics` manually `Pkg.develop`'d from a sibling checkout on disk -- something no fresh CI runner has. Confirmed the exact error by reproducing it directly (a clean depot, `git archive HEAD`, `Pkg.instantiate()`), and confirmed the fix the same way: an explicit `Pkg.develop(url="https://github.com/MSALabs/TSAnalytics.jl")` step (TSAnalytics.jl is a public repo, confirmed directly) added to both `.github/workflows/CI.yml` and `Docs.yml`, before `Pkg.instantiate()`/`julia-buildpkg` in each. ## Extended test suite, Stage 1 (2026-08-29): a genuine R/Python cross-validation harness

A separate, deliberately much larger effort from everything above: rather than more bug-fixing, this added an entirely new, opt-in test tier (`test/extended/`, gated behind `SEASONALADJUSTMENT_EXTENDED_TESTS=1`, never run by a plain local `Pkg.test()`) that runs matched specs through Julia's `x13()`, R's `seasonal::seas()`, and Python's `statsmodels.tsa.x13.x13_arima_analysis` -- all three pointed at the exact same real `x13ashtml` binary this package already manages -- and compares the numeric output. This is a genuine independent-wrapper agreement check, not a second computation (R and Python don't compute anything the binary itself doesn't, per this project's own established Part 1 verification philosophy), but it directly tests something nothing before this could: that `X13Spec`/`render`'s option mapping actually matches what R's and Python's own established wrappers mean by the "same" option, not just that the binary runs without erroring.

**Neither R nor Python (with the needed packages) existed anywhere in this environment before this session** -- both had to be stood up from nothing, in the same WSL sandbox already used for real-binary Linux testing throughout this project:

- **R**: no system R, and no passwordless `sudo` in this WSL sandbox (`apt install r-base` isn't available non-interactively). This package's own `x13ashtml` binary variant (the *only* Linux variant `x13org/x13prebuilt` ships at all, confirmed via its GitHub API contents listing -- there is no plain `x13as` to substitute) writes `_err.html`/a full HTML report instead. Separately, `statsmodels` also needs the binary to be found under one of a fixed set of names (`x13as`/`x12a`/`x13as_html`, confirmed via `statsmodels.tsa.x13._binary_names`) -- `x13ashtml` isn't among them, so `crossval_helpers.jl` creates a same-named symlink lazily.

1. **R's `regression.aictest` silently defaults to `c("td","easter")`, adding real regression effects, even when `regression.variables=NULL` is passed.** The first matched-spec attempt showed a genuine ~3-unit-magnitude discrepancy on the airline series traced, via `seasonal`'s own `static()` spec-inspection function, to this -- not a rounding issue. Fixed by requiring `r_helper.R`'s JSON contract to set `aictest` explicitly (as `[]` when not wanted) on every case.
2. **`outlier=NA` is invalid R syntax** ("missing value where TRUE/FALSE needed") -- to enable `seas()`'s own default outlier detection, the `outlier` argument must be entirely *absent* from the call, not set to any sentinel value; to disable it, `outlier=NULL` must be a real list element (confirmed directly that `existing_list$outlier <- NULL` afterwards *removes* the key instead of setting it -- the two cases build genuinely different list literals in `r_helper.R`, not one mutated in place).
3. **`r_helper.R` never actually wired up the `trading` JSON field at all** -- an outright omission, caught only because R's trading=true output was byte-identical to its trading=false output for the same nominal case, while Julia's genuinely differed. 4. **A run can report success (no `ERROR:`) while still not producing every requested output table.** Isolated to SEATS declining a non-admissible fixed ARIMA model on a short series while the overall exit stays clean, just a `WARNING:` -- `_run_julia` in `test_x13_crossval.jl` now explicitly checks every requested table file exists, not just `result.success`, treating a missing table the same as an explicit binary error for comparison purposes.

7. **`maxorder`'s widest search depth `(4,2)` needs real margin above `validate!`'s bare 36-month minimum, confirmed via two distinct real binary errors, not assumed.** `test_spec_extreme.jl`'s own real-binary spot check first used a 48-month series and hit "A model estimation error has occurred ... for a constant term" on a perfectly linear/seasonality-free series; switching to a genuinely seasonal 48-month series instead surfaced a second, more specific real error: `"Number of observations after differencing ... is 48, which is less than the minimum series length required for the model estimated, 51"` -- `(4,2)`'s own fitted model needs more than 48 observations once actually estimated, independent of `X13Spec`'s bare-minimum check. Fixed by using 72 months for that specific case, real margin above the confirmed 51-observation floor.

## Quarterly interval support (2026-08-29): period=4 threaded through the whole package, not just accepted at the spec layer

Directly continuing from the "Does R/Python support quarterly interval?" investigation this session -- confirmed directly against the real binary, not assumed, that X-13ARIMA-SEATS accepts EXACTLY two seasonal periods for seasonal adjustment: **period=12 (monthly) or period=4 (quarterly)**, and no others (`"ERROR: Seasonal period must be 4 or 12 if a seasonal adjustment is done"`, hit directly testing every other plausible value: 1, 2, 3, 6, 24, 52). R's `ts(..., frequency=4)`/`seas()` and Python's `pandas.date_range(freq="QS")`/`x13_arima_analysis` both confirmed directly to genuinely support quarterly too -- this is a real, well-trodden capability of the underlying methodology this package had simply never wired up, not new ground for X-13 itself.

**`X13Spec`** (`src/spec.jl`) gained a `period::Int` field (default `12`, keyword-constructor default preserved for full backward compatibility -- every existing call site that doesn't mention `period` behaves identically to before). `validate!` gained two new/generalized rules: (1) `period` must be `4` or `12`, with the real binary's own error text quoted; (2) `start[2]` (the subperiod) must fall in `1:period`. The two existing length-based rules were generalized rather than left monthly-only: the minimum-length rule is now `n >= 3*period` (36 for monthly, 12 for quarterly -- the SAME "3 complete years" requirement, confirmed the binary's own error wording is identical for both, just scaled), and `regression_user`'s forecast-horizon-coverage rule is now `n + period` (was hardcoded `n + 12`). `render` emits `period = $(spec.period)` in the `series{}` block.

**`parse_table`/`parse_output`** (`src/parse.jl`) gained a `period::Int=12` keyword. Confirmed directly against a real quarterly fixture: quarterly output tables use the exact same 6-character date width as monthly (`YYYYMM`), just with the trailing two digits meaning quarter-number (01-04) rather than month-number -- `parse_table` now interprets those trailing digits according to `period`, mapping a quarter to the `Date` of its first month (Q1->month 1, Q2->month 4, Q3->month 7, Q4->month 10) rather than always reading them as a month 1-12. An out-of-range trailing value (e.g. `"05"` for `period=4`) throws a clear `ErrorException`, not a silent misparse.

**`x13()`** (`src/api.jl`) gained a `period::Int=12` keyword, threaded through to `X13Spec`, `parse_output`, and the raw `parse_table` call used for `residuals`. `start` inference from `index` (when neither `start` nor `period`-mismatched data is given) now derives a quarter number (`(month-1) ÷ 3 + 1`) instead of a month number when `period=4`.

**Calendars/regressors** (`src/calendars.jl`) gained quarterly tiling: a new `_quarterly_periods` (3-month blocks anchored at the calendar quarter containing `from`/`to`, mirroring `_monthly_periods`'s own whole-period-tiling behavior) and a shared `_periods_for(freq, from, to)` dispatcher. `trading_day_regressors`, `easter_regressor`, and `custom_holiday_regressor` all gained (or already had, in `trading_day_regressors`' case, but unimplemented) a `freq::Symbol` keyword now genuinely accepting `:quarter` alongside `:month`. **One confirmed, honestly-documented gap, not silently glossed over**: X-13's own quarterly `.rmx` export for `td` has a 7th column ("Leap Year") that monthly's does not (confirmed directly against the real binary); `trading_day_regressors` always returns 6 columns for either `freq`, so it is not a byte-for-byte replica of X-13's own internal quarterly `td` regressor -- fine for feeding a *user*-defined regressor (X-13 doesn't require the extra column there), documented as a real gap in the function's own docstring rather than silently mismatched.

**Real-binary verification, same pattern as every prior finding**: SEATS/`automdl` on quarterly data hit the SAME class of issue already documented for the monthly `maxorder=(4,2)` case -- a perfectly deterministic synthetic series (first a pure sine wave, then a hand-rolled two-sine "pseudo-random-looking" perturbation) produces zero/near-zero residual variance once ARIMA fits it, and both SEATS (`"Cannot generate autocorrelations from a series of zeros"`) and `automdl` (`"Cannot make a choice of seasonal ARMA order due to model estimation errors"`) genuinely fail on it -- not a quarterly-specific bug, the same underlying cause hit twice now. Fixed the same way both times: real `Random.MersenneTwister`-seeded Gaussian innovations, not a merely-irregular-looking deterministic formula.

### The one finding worth flagging above everything else in this row: a real architectural bug, caught only by testing with a REAL backend

Implementing `residplot`/`monthplot`/`spectrumplot` exactly as the handoff specified (`@recipe function f(::Type{Val{:residplot}}, r::X13Result; ...)`, a plain "series-type recipe") **compiled cleanly, passed every `RecipesBase.apply_recipe`-based structural test, and was silently, completely broken**: `residplot(r)` rendered `plot(r)`'s own two line series instead of the residual data -- confirmed by actually installing Plots.jl+GR in WSL (a real, from-scratch install, ~380s precompiling ~110 packages) and hashing the rendered PNGs: `plot(r)`, `residplot(r)`, `monthplot(r)`, `monthplot(r; choice=:irregular)`, and `spectrumplot(r)` all produced the exact same 38857-byte, same-SHA256 image.

**Root cause, traced into `RecipesPipeline`'s own source, not guessed**: `X13Result` already has its own bare TYPE recipe (for plain `plot(r)`). `RecipesPipeline.jl`'s `_process_userrecipes!` calls `RecipesBase.apply_recipe(plotattributes, args...)` -- dispatch on ARGUMENT TYPES alone, matching my `f(r::X13Result; ...)` method unconditionally, before `plotattributes[:seriestype]` (already set to `:residplot` by `@shorthands`' own generated call) is ever consulted. A series-type recipe only gets a chance to fire in a LATER pipeline stage, keyed off an individual SERIES' own `seriestype` attribute -- and my type recipe's own series all explicitly set `seriestype := :path`, never `:residplot`, so that later stage never triggers either. Two recipes sharing one argument type this way is architecturally impossible to resolve via `seriestype` alone.

**Fix**: `RecipesBase.@userplot` -- the standard Plots.jl-ecosystem pattern for exactly this "named plot for a type that already has its own generic recipe" situation. `@userplot ResidPlot` generates a small wrapper struct (confirmed directly from `RecipesBase.jl`'s own source: `funcname = Symbol(lowercase(string(typename)))`, so `ResidPlot`->`residplot`, and `export $funcname, $funcname!` is generated automatically -- no manual `export residplot` needed in `SeasonalAdjustment.jl` itself, confirmed and cleaned up). `residplot`/`monthplot`/`spectrumplot`'s recipes now dispatch on their own wrapper type (`rp::ResidPlot`, reading `r = rp.args[1]`), a genuinely different type from `X13Result`, sidestepping the conflict by construction -- re-verified with the same real Plots.jl+GR install: all five renders now produce genuinely distinct SHA256 hashes.

**A second, equally real lesson from the same investigation**: the Level 1 structural tests (`RecipesBase.apply_recipe(Dict(), Val{:residplot}, r)`, calling the series-type method directly with an explicit `Val{}` argument) **could never have caught this bug**, passing or failing -- that call form bypasses the exact argument-type ambiguity that only manifests through the real `residplot(r)` -> `plot(...)` entry point. `test/test_plots.jl`'s own `_apply_named` helper was rewritten to construct the real wrapper type (`ResidPlot((r,))`) instead, but even that still doesn't route through the actual exported `residplot(...)` function/`Plots.plot` machinery. A genuine real-backend smoke test (`test/extended/test_plots_backend.jl`, gated on `Base.find_package("Plots") !== nothing` -- Plots.jl is deliberately NOT added to this package's own `Project.toml`/`[extras]`, confirmed that would force every plain `Pkg.test()` to resolve it; the file skips cleanly, not a failure, when absent) is the only level that actually exercises the real call path, and now asserts every recipe's rendered PNG is pairwise byte-distinct from every other -- the exact regression guard this bug needed.

## W.7 -- forecasts, missing values, components, vcov/coeftable/summary/update, force/seasonalma, sliding spans/history (2026-08-31)

Full implementation of `handoff/w7-functionality-gaps-handoff.md` (all 8 deliverables) plus the reference catalogue it depends on, `handoff/x13-saveable-tables.md`. Verified against the real binary throughout via WSL; the source handoffs were cross-checked against the actual codebase first (per this project's own standing practice), which surfaced a real, pre-existing bug before any new feature work started.

**W.7.1 -- the 281-table catalogue and a real, confirmed routing bug.** `src/known_tables.jl` is generated (`tools/generate_known_tables.jl`, never hand-edited) by parsing `handoff/x13-saveable-tables.md`'s own markdown tables directly -- 278 unique table-keyword entries after deduplicating the handful of extensions that appear under more than one X-13 spec block (`.b1`: series vs. composite; `.tac`: x11 vs. seats; document order breaks the tie, preferring the block this package actually supports). Reviewing `render()` before adding anything new surfaced a real, already-shipped bug: every `save` table was dumped unconditionally into `x11{}`/`seats{}` regardless of which spec block actually owned it -- `save=[:hol]` (a `regression{}` table) rendered `x11 { save = (hol) }`, which the real binary rejects. Fixed by grouping `spec.save` per-block (`_save_by_block`) and routing each table to its real block: `series`/`regression`/`estimate`/`outlier`/`x11`/`seats` get typed rendering paths; every other block (`forecast`, `check`, `force`, `slidingspans`, `history`, ...) merges into `spec_args` as a synthetic `"blockname.save"` entry. `validate!` gained a new rule: every `save` symbol must be in the generated catalogue, with a distinct error for the five print-only keywords (`none`/`all`/`alltables`/`default`/`brief`) that are valid for `print` but never `save`. `series()`'s re-run machinery (`_ensure_saved`, factored out and shared with the new `vcov`/`components`/`_spectrum_series`) now shares one implementation instead of `_spectrum_series` keeping its own separate re-run path.

**W.7.2 -- forecast/backcast.** `.fct`/`.bct` are a real, confirmed 4-column format (`date\tpoint\tlowerci\tupperci`, tab-separated, both already on the original scale) -- distinct from both `parse_table`'s 2-column and the spectrum tables' 3-column shape, needing its own `_parse_forecast_table`. `forecast(r; level=0.95)`/`backcast(r; level=0.95)` re-run whenever the requested `level` differs from whatever `forecast.probability` the original run used, not just when the table is missing (level genuinely changes the binary's own output). `maxlead` is a new typed `X13Spec` field specifically so `validate!` can enforce X-13's own `pfcst=120` program limit before any subprocess; `pobs=780` (max series length) is enforced the same way. `pureg`/`pb` are deliberately NOT enforced -- structurally unreachable (one named user regressor) or unknowable before a run (automdl-detected outliers), a real, stated scope decision rather than a vacuous check.

**W.7.3 -- missing values.** `x13(y; missing_action=:error|:x13|:omit)`. `:x13` substitutes X-13's own `-99999` sentinel (warns if the series already genuinely contains that value); `:omit` drops only leading/trailing gaps, throwing on an interior one, and shifts the effective `start` forward by the trimmed count (`_advance_start`) so `result.dates` stays aligned. `Union{Missing,Float64}` needed a real workaround: `tsvalues(y)` itself errors trying to eagerly convert `Missing` to `Float64` for a plain vector, so `x13()` now detects `Missing <: eltype(y)` and skips straight to `_handle_missing` on `y` itself in that one case. **A genuinely surprising real finding, confirmed directly**: `missing_action=:x13` needs an explicit `transform` for the exact same reason any other regression content does (below) -- X-13 interpolates the sentinel via its own internal AO-style regressor, which is enough to trigger the log-transform requirement even though this package's own spec never renders a `regression{}` block for it.

**A real, broader validate! gap found and fixed along the way (not W.7-specific, but found here).** The existing rule 5 ("regression + multiplicative/log-additive x11_mode needs transform=:log") only fired for an EXPLICIT `x11_mode`. Confirmed directly against the real binary, across four separate combinations, that this missed the far more common case: X-13's own IMPLICIT default x11 mode (when `x11_mode` is left `nothing`) is ALSO multiplicative, and a plain `trading=true` spec with no explicit mode and no transform block hits the identical error. The more precise rule, also confirmed directly: it's specifically a MISSING transform block that fails -- `transform=:none` (an explicit no-op) runs successfully in the exact same combination. `validate!` now fires whenever `transform === nothing` and a regression block is present, unless `x11_mode` is `:additive`/`:pseudoadditive`.

**W.7.4 -- component-factor accessors.** `components(r; which=:all|:trading_day|:holiday|:user|:outlier|:ao|:ls|:tc|:so)`. `:trading_day`/`:user` get a cheap spec-level precheck (avoids a subprocess when the effect obviously isn't configured); the rest fall through to a real run. **A real, easily-mismade test mistake, caught and fixed**: a `usertype=:holiday` user regressor's factors land in `regression.holiday` (`.hol`), NOT `regression.userdef` (`.usr`) -- confirmed directly (`.usr` genuinely absent from the output directory on a successful run; `.hol` present under the identical spec with `save=[:hol]` instead). `.usr` is reached only by a user regressor with some other/no usertype.

**W.7.5 -- vcov/coeftable.** `StatsAPI.vcov(r)` reads `estimate.regcmatrix`/`estimate.armacmatrix` (`.rcm`/`.acm`, the COVARIANCE matrix under `save`, confirmed by `sqrt.(diag(V))` reproducing `stderror(r)` to ~0.8% -- calibrated from what was actually observed, not assumed 1e-6) via a new generic `_parse_matrix_table` (handles both `.rcm`'s and `.acm`'s slightly different row-label shapes by taking the trailing N fields as data regardless). Two more real findings, both from actually running the binary rather than trusting the handoff's single worked example: (1) `.rcm` is not written at all for exactly one regression coefficient (a 1x1 "matrix" apparently not considered worth a file); needs 2+ independent regression coefficients. (2) `trading=true` reports a 7th, DERIVED coefficient (`"Trading Day$Sun"`, implied by the other six) that `.udg`'s coefficient block includes but `.rcm`'s 6-row matrix does not -- `vcov` refuses to guess at the alignment in that case and throws a clear, named error rather than silently misaligning the matrix; documented as a real, honest scope limitation in its own docstring, not papered over. `StatsBase.coeftable(r)` (extends `StatsBase`'s own generic, used fully-qualified) gives Estimate/Std.Error/t-value straight from `.udg`'s own three-field coefficient lines -- no `vcov` needed for this much. p-values deliberately not included (would need a t-distribution CDF, the same open dependency question the W.8 handoff raises for a Q-Q plot panel). A THIRD real `_coefficient_lines` parsing trap found the same way as W.5's original `lbq$NN` one: `"chi$Trading Day"` (a joint significance chi-squared test for a regressor GROUP, not a coefficient) also has a `$` in its key and a 3-field value: excluded now alongside the lag-diagnostic families.

**W.7.6 -- summary/update.** `update(r; kwargs...)` is `X13Spec(r.spec; kwargs...)` re-run through a newly-factored-out `_run_spec` (the shared "write, run, parse into X13Result" tail `x13()` itself now also uses, rather than keeping two copies). `summary(r) -> X13Summary` composes existing accessors into one report with its own `show`. **`summary` is deliberately NOT exported** -- confirmed directly this is a real, deterministic collision, not hypothetical: `Base` already exports its own `summary` (a different, one-line-descriptive-string contract), so `using SeasonalAdjustment` genuinely ambiguates the bare name. Reached as `SeasonalAdjustment.summary(r)`, the same fully-qualified convention `coeftable`/`vcov` already use.

**W.7.7 -- force/seasonalma.** Real accepted keyword values confirmed directly against the binary rather than trusted from the handoff's own (explicitly flagged as unverified) guess: `force` is `:none`/`:denton`/`:regress`; `force_target`'s real spelling is **`:calendaradj`**, not `:caladjust` as the handoff's draft guessed -- settled by the binary's own error message ("Entry for forcetarget argument must be original, calendaradj, permprioradj, or both"). All 8 `seasonalma` spellings from the handoff's own guess (`s3x1`...`msr`) confirmed working verbatim, no translation needed.

**W.7.8 -- sliding spans / revision history.** Settles W.5's open question 3, directly: both land rich summary statistics in `.udg` itself (`ss*`/`s2.*`/`s3.*` for sliding spans; `r0N.lag00.*`/`revspan` for history), confirmed via a real `.udg` key diff against a baseline run -- no separate table parsing needed for the headline numbers. Given the sheer field count X-13 produces here, `slidingspans(r)`/`revision_history(r)` surface a handful of headline typed fields plus a `raw::Dict` escape hatch for everything else, rather than modeling every single one -- a deliberate scope decision, not an oversight.

**Two deterministic (not flaky) test-infrastructure bugs found only by running `Pkg.test()` repeatedly, both fixed**: `test/runtests.jl` never `import StatsBase`, so `StatsBase.coeftable` intermittently resolved depending on unrelated include-order side effects from other files; and the (since-fixed) `summary`/`Base.summary` export collision above surfaced as `UndefVarError` inside `Test.@testset`'s own exception handling, not a normal assertion failure -- neither would have been caught by a single passing run.

### S.1's own verified starting point — the Henderson filter formula

Already confirmed from two independent sources (a working reference
implementation and a US patent document, cross-checked against each
other):
```
For a symmetric Henderson filter of length n = 2m+1:
  m1 = (m+1)^2,  m2 = (m+2)^2,  m3 = (m+3)^2
  d  = 8*(m+2)*(m2-1)*(4*m2-1)*(4*m2-9)*(4*m2-25)
  w[j] = 315 * (m1-j^2) * (m2-j^2) * (m3-j^2) * (3*m2-11*j^2-16) / d
```
